La campagne établit désormais quatre faits expérimentaux distincts :

  [1] CAPACITÉ
      Un modèle 8B Q4_K_M peut être exécuté sur UNE SEULE session HTP0
      avec un RSS process mesuré à ~4.97 Go.

      Un modèle Qwen3.5 9B D2-A-MTP Q4_0 peut également être chargé
      sur une seule session HTP0 en ngl=99 :
          - construction du graphe : OK
          - pass4.5 : OK
          - 1831 nœuds
          - 4 splits
          - RSS observé au point de charge : 2.93 Go

      => la valeur vmem déclarée de 3.35 Go ne doit PAS être interprétée
         comme une limite directe du RSS observable du processus.

  [2] BANDE PASSANTE / MEMORY-WALL
      Le sweep 8B Q4_K_M donne :

          ngl      TG32        ms/token
          ───────────────────────────────
           16       6.66         150
           32       5.38         186
           48       4.86         206
           64       4.69         213
           80       4.08         245

      Ajustement :

          ms/token = 1.36 × ngl + 134.8
          R² = 0.958

      => relation quasi-linéaire entre volume de couches offloadées
         et temps de génération.

      BW_eff estimée selon hypothèse de masse/couche :
          ~81–104 GB/s

      MAIS cette conversion reste dépendante de la vraie masse transférée.
      La pente de 1.36 ms/couche est la mesure primaire fiable.

  [3] MULTI-HTP
      HTP0 / HTP1 / HTP2 sont bien accessibles.

      Cependant le mode :

          -dev HTP0,HTP1,HTP2

      dans llama-bench ne constitue PAS un calcul parallèle unique :
      le benchmark exécute le modèle séparément sur chaque device.

      Résultats typiques :

          HTP0 ≈ 5.39 t/s
          HTP1 ≈ 5.34 t/s
          HTP2 ≈ 4.46 t/s

      Les modes :

          -sm tensor
          -sm row

      n'ont produit aucun résultat exploitable (rc=0).

      => aucune accélération multi-HTP parallèle démontrée sur ce build.

      => les ~10–11.4 Go observés avec plusieurs sessions correspondent
         à une capacité d'adressabilité/mapping supérieure, PAS à une
         multiplication démontrée de la bande passante decode.

  [4] PIPELINE DSP / ERR=46
      Le 9B D2-A-MTP forcé sur HTP0 ngl=99 :

          CHARGE        OK
          GRAPH         OK
          EXECUTION     HANG
          op_pending    16
          last_err      46
          watchdog      180 s
          CDSP après     ALIVE

      Le draft-MTP produit également un pattern de hang avec :

          op_pending=4
          err=46

      => forte corrélation entre certaines configurations et un blocage
         du chemin RPC/DSP.

      ATTENTION :
      "16 ops = limite physique exacte de la file" n'est PAS encore
      démontré. Le profil disponible ne permet pas encore d'identifier
      avec certitude l'opération racine.

      Il faut donc distinguer :

          FAIT :
              err=46 + op_pending élevé + SPIN reproductible

          HYPOTHÈSE :
              saturation de la file d'opérations in-flight

1. CORRECTION DU 0x80000600
──────────────────────────────────────────────────────────────────────────────────────

Symptôme initial :

      failed to open domain 3 (HTP)
      0x80000600

Diagnostic initial :
      suspicion de CDSP/NSP bloqué nécessitant power-cycle.

Diagnostic corrigé :

      problème d'environnement dynamique.

Configuration fautive :

      LD_LIBRARY_PATH contenant des chemins /vendor
      et/ou environnement non conforme au chemin HTP attendu.

Configuration fonctionnelle :

      LD_LIBRARY_PATH=/data/local/tmp/npu
      ADSP_LIBRARY_PATH=/data/local/tmp/npu

      SANS ajouter /vendor dans ces chemins.

Le D2-A-MTP a alors démarré réellement sur HTP0.

=> Le 0x80000600 étudié dans cette campagne n'était PAS une
   incompatibilité du modèle avec HTP.

5. BW_EFF — ESTIMATION
──────────────────────────────────────────────────────────────────────────────────────

Deux hypothèses de masse/couche ont été utilisées.

Hypothèse A :

      ~0.15 Go/couche
      => BW_eff ≈ 104 GB/s

Hypothèse B :

      ~0.11 Go/couche
      => BW_eff ≈ 81 GB/s

Fourchette :

      ~81–104 GB/s

Valeur à retenir scientifiquement :

      1.36 ms/couche

Pourquoi ?

      ngl n'est qu'un proxy du volume réel.

      Les couches peuvent avoir des masses différentes.
      Les quantifications Q4_K_M ne correspondent pas nécessairement
      à une masse uniforme.
      Le volume réel transféré doit être mesuré pour produire
      une BW absolue.

Conclusion :

      BW_eff ~100 GB/s = ESTIMATION
      pente 1.36 ms/couche = MESURE ROBUSTE

      RSS ≈ 4.97 Go

Observation :

      vmem déclarée ≈ 3.35 Go

      MAIS

      RSS ≈ 4.97 Go

Donc :

      vmem déclarée ≠ limite directe du RSS process.


Interprétation correcte :

      HTP session
          |
          +-- domaine virtuel déclaré
          |
          +-- mappings
          |
          +-- buffers
          |
          +-- mémoire partagée
          |
          +-- allocations CPU/runtime
          |
          +-- RSS process

Le RSS ne peut donc pas être assimilé directement à
"mémoire HTP effectivement utilisée".

Conclusion robuste :

      le backend autorise effectivement un footprint process
      supérieur à la vmem déclarée de 3.35 Go.

8. ERR=46 — HYPOTHÈSE À NE PAS SURINTERPRÉTER
──────────────────────────────────────────────────────────────────────────────────────

Deux expériences produisent une signature commune :

      D2 ngl99 :
          op_pending=16
          err=46

      draft-MTP :
          op_pending=4
          err=46

Cela suggère un problème commun du chemin DSP/RPC.

Mais :

      ERR=46
      ≠ preuve automatique d'une "queue pleine"

La formulation correcte du rapport est :

      "Le hang est reproductible et associé à un nombre élevé
       d'opérations en attente et à err=46."

Puis :

      "Une saturation du pipeline d'opérations in-flight constitue
       une hypothèse forte, mais reste à démontrer par instrumentation
       plus fine ou modification expérimentale du niveau de concurrence."

19. CONCLUSION SCIENTIFIQUE ACTUELLE
──────────────────────────────────────────────────────────────────────────────────────

La campagne ne montre PAS un simple problème de "mémoire insuffisante".

Elle montre un système à plusieurs plafonds :

      CAPACITÉ
          ↓
      suffisamment élevée pour charger le 8B HTP0
      et construire le 9B HTP0.

      BANDE PASSANTE EFFECTIVE
          ↓
      comportement decode fortement volume-bound.

      RUNTIME / PIPELINE DSP
          ↓
      certaines configurations hybrides/Mamba/MTP provoquent
      err=46 et un SPIN reproductible.

      MATMUL / HMX
          ↓
      composante encore insuffisamment instrumentée.

La conclusion la plus robuste aujourd'hui est donc :

      "Le plafond observé du GGML-HTP n'est pas réductible
       à une simple limite de capacité mémoire."

Le decode 8B montre un memory-wall empirique.

Le 9B/Mamba révèle en parallèle une limite du chemin d'exécution DSP.

Le prochain test déterminant est donc le **A/B du chemin HMX matmul**,
avant de déclarer MXFP4 comme solution définitive.
