2. CONTEXTE TECHNIQUE ETABLI
--------------------------------------------------------------------------------

M1 - REPACK DES POIDS AU CHARGEMENT

  GGML_TYPE_Q4_0  -> repack_q4_0_tiled()  -> Q4_0_TILED
  GGML_TYPE_Q4_1  -> repack_q4_1_tiled()  -> Q4_1_TILED
  GGML_TYPE_Q8_0  -> repack_q8_0_tiled()  -> Q8_0_TILED
  GGML_TYPE_IQ4_NL -> repack_q4_0_tiled()
  GGML_TYPE_MXFP4  -> repack_mxfp4_tiled()

Le backend ne promeut pas un poids Q4 en Q8.
Le format de quantification du poids est conserve lors du repack.

M2 - QUANTIFICATION RUNTIME DES ACTIVATIONS

Pour les chemins HVX quantifies :

  activation F32 -> quantize_f32_q8_0_tiled()

Pour Q4_0 et Q8_0, la meme quantification d'activation Q8_0_TILED est
utilisee. La variante Q4_1 utilise Q8_1_TILED.

Donc, dans l'essai attnQ4 :

  poids      = Q4_0_TILED
  activation = Q8_0_TILED

Ce sweep NGL ne cherche PAS a modifier cette precision d'activation.

9. HYPOTHESES DISCRIMINANTES
--------------------------------------------------------------------------------

H1 - PIPELINE / OFFLOAD BOUND

  Le TPS presente un optimum pour un NGL intermediaire.
  Un NGL trop eleve augmente le cout CPU / transferts / synchronisation.

H2 - HTP LIMITED

  Le TPS continue d'augmenter avec NGL jusqu'a une valeur elevee.
  La partie CPU limite le debit seulement apres un certain seuil.

H3 - BOTTLENECK AILLEURS

  Le TPS reste quasi plat sur une large plage de NGL.
  Le goulet d'etranglement est alors probablement lie au pipeline, a la RAM,
  aux synchronisations ou au cout des kernels plutot qu'au seul partage HTP/CPU.

goulet d'etranglement du backend.
