2. Important Terminology
2.1 HTP / NPU
In this report, HTP refers to Qualcomm Hexagon Tensor Processor execution through the GGML Hexagon backend.

"NPU" is used as the higher-level description of the accelerator.

Therefore:

HTP ≈ Qualcomm Hexagon tensor accelerator
NPU ≈ architectural/general term

The report should not interpret "HTP 32-bit" as automatically meaning that the HTP can only address 4 GiB of memory. Data-path width, accumulator width, pointer width, tensor representation, vector width, and memory addressing are different concepts.

9. Thermal Measurement Protocol
This is one of the most important corrections to the benchmark methodology.

Earlier sweeps were performed without sufficient thermal control. The GPU reached approximately:

68–70°C

and DDR reached approximately:

72°C

while GPU utilization remained around:

93%

Consequently, a sequence of benchmarks executed without cooling cannot be treated as a clean comparison.

10. Correct Thermal Signals
The following distinction is critical.

cpu-hw-trip = 95°C

is a thermal trip/alarm threshold.

It is not the actual GPU operating temperature.

For GPU thermal control, the relevant signal is:

gpuss

Example:

GPU ≈ 70°C

This is the signal that should be used by the thermal governor.

11. Cold-Start Protocol
Every benchmark intended for comparison should follow:

1. Stop previous workload.
2. Allow device to cool.
3. Verify GPU temperature.
4. Start only when GPU < 55°C.
5. Run warm-up if required.
6. Record temperature before benchmark.
7. Execute benchmark.
8. Record temperature during/after benchmark.
9. Record throughput.
10. Allow cooling before next candidate.

A benchmark sequence without cooling should be explicitly labeled:

WARM / THERMALLY CONTAMINATED

and should not be mixed with cold measurements.

12. Thermal Governor
The current governor strategy is:

GPU temperature

      < 50°C
        │
        ▼
   GPU preferred
        │
        │
        │ 50–65°C
        │
        ▼
 keep previous decision
        │
        │
      > 60°C
        │
        ▼
   HTP/NPU preferred

The operational configuration currently used is approximately:

GPU → HTP/NPU transition: 60°C
HTP/NPU → GPU transition: 50°C

This creates hysteresis.

The purpose is to avoid:

GPU → NPU → GPU → NPU → ...

oscillation around a single threshold.

13. Why Thermal Switching Matters
The measured D2-A results show:

Cold HTP0:  8.90 t/s at ~41°C
Warm HTP0:  8.22–8.37 t/s

The difference is approximately:

8.90 → 8.22

≈ -7.6%

or, depending on the warm measurement:

8.90 → 8.37

≈ -6.0%

Therefore temperature is not merely a power-consumption metric.

It directly changes inference throughput.

A thermal governor can consequently be viewed as a performance controller:

temperature
     ↓
backend selection
     ↓
frequency / thermal state
     ↓
decode throughput

14. Dynamic GPU ↔ NPU Strategy
The long-term strategy is not necessarily:

GPU forever

or:

NPU forever

but potentially:

GPU while thermally efficient
        ↓
GPU temperature rises
        ↓
switch workload toward HTP
        ↓
GPU cools
        ↓
return workload toward GPU

This can be implemented at different granularities.

Phase-level switching
Simplest:

prefill → GPU
decode → HTP

or:

decode block A → GPU
decode block B → HTP

Block-level switching
More advanced:

layers 0–N     → HTP
layers N–end   → GPU

and dynamically change the boundary according to temperature.

Operator-level switching
Most flexible but potentially expensive:

MUL_MAT → GPU
RMS_NORM → HTP
ATTENTION → HTP
...

This has a major risk:

more backend boundaries
        ↓
more synchronization
        ↓
more transfers
        ↓
lower throughput

Therefore thermal switching should prefer large contiguous blocks rather than rapidly alternating individual operators.

20. Causal Explanation of 0.96 t/s
The measured chain is:

Q4_K_M
   ↓
HTP rejects heavy MUL_MAT
   ↓
MUL_MAT fallback
   ↓
~10875 CPU MUL_MAT splits
   ↓
3 HTP devices execute small fragments
   ↓
CPU ↔ HTP/OpenCL synchronization
   ↓
massive fragmentation
   ↓
0.96 t/s

This is a much stronger explanation than simply stating:

"three HTP devices run out of memory."

The logs directly show the CPU fragmentation.

27. Boundary-Cost Model
A useful abstraction is:

Total latency =
    Σ compute_cost(layer, backend)
  + Σ transfer_cost(boundary)
  + Σ synchronization_cost(boundary)
  + spill_penalty

Therefore the governor should not optimize only:

HTP percentage

but rather:

layer placement
+
backend cost
+
boundary cost
+
thermal state
+
memory pressure

28. Why Large Blocks Are Preferable
The experiments strongly support large contiguous backend regions.

Preferred:

HTP
████████████
             │
             │ one boundary
             ▼
             GPU
             █████████████████

Avoid:

HTP → GPU → HTP → GPU → HTP → GPU

because every transition can introduce:

synchronization
buffer management
data movement
scheduler overhead

Therefore the thermal governor should, when possible, move the boundary between large blocks rather than alternate individual operators.

30. Thermal State Machine
A reproducible first implementation can use:

             GPU < 50°C
                  │
                  ▼
             GPU preferred
                  │
                  │
                  │ GPU ≥ 60°C
                  ▼
             HTP preferred
                  │
                  │
                  │ GPU > 50°C
                  │
                  │ keep HTP
                  │
                  ▼
             GPU cools
                  │
                  │ GPU < 50°C
                  ▼
             GPU preferred

The key property is hysteresis:

GPU → HTP : 60°C
HTP → GPU : 50°C

31. Thermal Governor Pseudocode
Conceptually:

if gpu_temp >= 60; then
    mode=HTP
elif gpu_temp <= 50; then
    mode=GPU
else
    mode=$previous_mode
fi

The actual implementation must also avoid restarting the inference engine unnecessarily.

A backend switch should preferably happen at a natural execution boundary.

32. Important Constraint: Do Not Oscillate
A bad governor would behave like:

59.9°C → GPU
60.1°C → HTP
59.9°C → GPU
60.1°C → HTP
...

This is unacceptable because the switching overhead can exceed the thermal benefit.

The governor must therefore include:

hysteresis;
minimum dwell time;
optional minimum number of generated tokens between decisions;
cooldown confirmation;
backend-switch cost.
A more robust state machine is:

GPU state
   │
   │ temp > 60°C for N samples
   ▼
HTP state
   │
   │ temp < 50°C for N samples
   ▼
GPU state

33. Temperature Is Not the Only Trigger
Temperature should not be treated as the sole scheduling variable.

The decision should ideally consider:

The simplest production governor can start with temperature only and progressively add these signals.

40. Allocation / Scheduler Bug Detection
A separate GGML investigation found a real allocator correctness bug.

The adversarial test constructs:

graph A

for reservation and:

graph B

for allocation.

The graphs have:

same number of nodes
same number of leaves
same tensor sizes

but different tensor lifetime/topology.

The old allocator could accept the stale plan.

Observed:

m0.data == m1.data

while both tensors were simultaneously live.

This proves silent memory-plan corruption.

41. Allocator Diagnostic
A debug signature was added using FNV-1a.

The signature includes:

operation
tensor dimensions
view source
buffer ID
source tensors

It is populated during reservation and checked during reallocation.

A mismatch produces:

GGML_LOG_ERROR

The diagnostic is deliberately:

log-only

It does not automatically force a re-plan.

This distinction is important:

hash mismatch
    ≠
proof that a new plan is valid

The tool is therefore a detector, not a repair mechanism.

43. Why the Allocator Fix Matters to Heterogeneous Scheduling
The scheduler creates backend-dependent graph topology.

Therefore:

same tensor sizes
        ≠
same memory plan

and:

same model
        ≠
same graph

when backend placement changes.

This is especially relevant to:

MTP draft/verify
HTP/GPU layer splits
dynamic scheduling
thermal backend switching

A stale allocator plan could otherwise create silent corruption when the graph topology changes.

             GPU/HTP mix                    HTP-heavy

The actual placement should then be selected using the layer cost model.

47. Recommended Cost Model
For each layer:

layer_id
operator_types
quantization
weight_bytes
activation_bytes
HTP_latency
GPU_latency
CPU_latency
transfer_bytes
synchronization_cost
thermal_sensitivity
spill_risk

The estimated cost becomes:

Cost(P) =
    Σ compute(layer, backend)
  + λtransfer · transfer_bytes
  + λsync · synchronization
  + λspill · spill_penalty
  + λthermal · thermal_penalty

48. Thermal-Aware Cost Model
The model can be extended:

Cost(layer, backend, temperature)

For example:

GPU cost at 41°C
        <
GPU cost at 70°C

if thermal throttling reduces GPU frequency.

The same approach can be applied to HTP if corresponding thermal/performance telemetry becomes available.

49. Dynamic Layer Boundary
For a contiguous split:

layers 0 ... N     → HTP
layers N+1 ... L   → GPU

the governor can optimize:

N

rather than independently assigning every layer.

This drastically reduces the search space.

Example:

N = 10
N = 20
N = 30
...

rather than:

2^L possible assignments

for an L-layer model.

50. Thermal-Aware Boundary Movement
A promising strategy is:

Cold GPU:
    GPU-heavy boundary

GPU warming:
    move boundary toward HTP

GPU hot:
    HTP-heavy boundary

GPU cooling:
    slowly move boundary back toward GPU

The transition should occur only at safe graph/execution boundaries.

This preserves the large-block principle.

51. Avoiding Excessive Dynamic Switching
The governor must never optimize temperature at the expense of inference throughput.

Therefore each transition should have:

switch_cost

and a minimum dwell time.

A decision can be expressed as:

switch if:

expected_performance_gain
>
switch_cost + hysteresis_margin

This is preferable to a simple temperature threshold alone.

56. Key Conclusions
Conclusion 1 — Quantization determines backend suitability
The experiments demonstrate:

Q4_K_M → GPU
Q4_0/Q8_0 → HTP

for the tested workloads.

This is driven by backend/operator support, not merely model size.

Conclusion 2 — More HTP is not automatically faster
Qwen3-4B:

1 HTP → 13.71
2 HTP → 14.59
3 HTP → 18.86

but Qwen3-8B Q4_K_M:

1/default → 6.72
2 HTP → ~4.55
3 HTP → 0.96

Therefore HTP scaling is workload-dependent.

Conclusion 3 — CPU fallback can dominate heterogeneous execution
The 3-HTP Q4_K_M experiment directly showed:

~10875 CPU MUL_MAT splits

with:

0 HTP MUL_MAT

This creates the fragmentation responsible for the 0.96 t/s result.

Conclusion 4 — Large backend blocks are preferable
The layer-split experiments demonstrate that:

backend boundary position

is a major performance variable.

Large contiguous regions are preferable to frequent switching.

Conclusion 5 — Thermal state is a performance variable
D2-A:

41°C → 8.90 t/s
warm → 8.22–8.37 t/s

Therefore thermal management must be integrated into performance scheduling.

Conclusion 6 — Thermal GPU→HTP switching is viable
A first practical governor is:

GPU >= 60°C → HTP-heavy
GPU <= 50°C → GPU-heavy
50–60°C → keep current mode

This should be implemented with minimum dwell time and large execution blocks.

Conclusion 7 — MTP currently provides the largest throughput gain
D2-A:

HTP0 = 8.90 t/s

D2-A + MTP:

~16.2 effective t/s

with:

52.9% draft acceptance
2.50 mean draft length

This is currently the strongest measured configuration.
